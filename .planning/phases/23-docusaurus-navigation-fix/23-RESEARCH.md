# Phase 23: Docusaurus Navigation Fix - Research

**Researched:** 2026-02-24
**Domain:** Docusaurus 3.x MDX processing, Doxygen XML to Markdown generation
**Confidence:** HIGH

## Summary

This phase fixes two distinct problems in the API documentation pipeline. The primary bug (DOC-02) is in `scripts/generate-api-docs.js`: prose description text (`briefDesc`, `detailedDesc`) is extracted from Doxygen XML and written directly to Markdown without MDX escaping. The `xml2js` parser decodes XML entities like `&lt;TPixel&gt;` into raw `<TPixel>`, which lands unescaped in generated `.md` files. The existing `escapeForMdx()` function is already present and correct — it is simply not being called on prose text output paths. The secondary issue (DOC-01 related) is that `config.modules.utils.classes` in the generator incorrectly includes namespace names (`Colors`, `DrawingHelpers`, `Noise`, `Polar`, `Signals`), causing spurious "Warning: XML file not found" messages on every regeneration.

The current build passes zero-error because Docusaurus 3.9.2 with `markdown.format: 'detect'` routes `.md` files through the `'md'` processor (CommonMark + `rehype-raw`), which tolerates raw HTML tags. However, the unescaped `ICanvas<TPixel>` in `docs/api/graphics/CanvasExtended.md` is a live defect that will silently corrupt future docs if the format config ever changes. More importantly, DOC-02 requires escaping in the generator itself, not just in output files, so re-running generation keeps the result clean without a separate post-processing step.

Navigation (DOC-01) is currently functional: the autogenerated sidebar (`api-sidebar.js: { type: 'autogenerated', dirName: '.' }`) picks up all 85 files in `docs/api/`, the sidebar ID `apiSidebar` matches the navbar config `docsPluginId: 'api'`, and `npm run build` with `onBrokenLinks: 'throw'` completes successfully. The navigation defect is the spurious class-lookup warnings that pollute generator output, making future safe-regeneration impossible to verify cleanly.

**Primary recommendation:** Apply `escapeForMdx()` to all prose text extraction points in `generate-api-docs.js`, remove namespace names from `utils.classes`, regenerate all API docs, verify build is zero-error and zero-warning.


### Pattern 1: escapeForMdx at extraction time
**What:** Wrap `extractText()` calls that produce prose output in `escapeForMdx()` at the variable assignment site, so every downstream use is already safe.
**When to use:** Every place a Doxygen description string goes into a markdown template.
**Example:**
```javascript
// Source: scripts/generate-api-docs.js — processClass()
// BEFORE (unsafe):
const briefDesc = extractText(compound.briefdescription);
const detailedDesc = extractText(compound.detaileddescription);

// AFTER (safe):
const briefDesc = escapeForMdx(extractText(compound.briefdescription));
const detailedDesc = escapeForMdx(extractText(compound.detaileddescription));
```

The same pattern applies to method/function `briefDesc`/`detailedDesc` inside the member loop:
```javascript
// BEFORE:
briefDesc: extractText(member.briefdescription),
detailedDesc: extractText(member.detaileddescription),

// AFTER:
briefDesc: escapeForMdx(extractText(member.briefdescription)),
detailedDesc: escapeForMdx(extractText(member.detaileddescription)),
```

### Pattern 2: Namespace names do NOT belong in modules.classes
**What:** `config.modules.utils.classes` currently lists namespace names (`Colors`, `DrawingHelpers`, `Noise`, `Polar`, `Signals`). These are already in `config.namespaces` and processed by `processNamespace()`. They have no `classenjin2_1_1X.xml` file, so `processClass()` logs "Warning: XML file not found for X" and returns null.
**When to use:** Never mix namespace names into `classes` arrays.
**Fix:** Remove the five namespace names from `utils.classes`:
```javascript
utils: {
  classes: ['InputSystem', 'math::TrigLUT'],  // namespaces handled by config.namespaces
  description: 'Utility functions and helpers',
},
```
The `processGroup()` function for utils/README.md already scans the actual output directory for `.md` files, so the README will correctly list all pages including the namespace pages.

### Anti-Patterns to Avoid
- **Escaping only in output files:** Running `sed` or find-replace on generated `.md` files satisfies the current build but breaks on every regeneration — violates DOC-02.
- **Changing `markdown.format` to hide the problem:** Setting `format: 'mdx'` per the api plugin config would expose failures; setting `format: 'md'` would hide the real bug. The fix must be in the generator.
- **Double-escaping:** `escapeForMdx()` converts `<` to `&lt;`. If called on text that was already XML-decoded by `xml2js`, this is correct. Do NOT call it on strings that already went through `formatType()` (which does its own escape cycle), or on method signatures that already go through `escapeForMdx()` in `formatMethod()`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTML entity encoding | Custom regex replacer | Existing `escapeForMdx()` in the same file | Already handles `<`, `>` correctly; just apply it |
| MDX format detection | Manual file extension checks | Docusaurus `format.js` / `markdown.format: 'detect'` in config | Already implemented correctly |

**Key insight:** The fix is trivially small — 8 call-site changes to wrap existing `extractText()` calls with the already-present `escapeForMdx()`. The bug is a call-site omission, not a missing capability.

## Common Pitfalls

### Pitfall 1: Double-escaping method signatures
**What goes wrong:** `formatMethod()` already calls `escapeForMdx()` at its return. If you also wrap method `briefDesc`/`detailedDesc` in `escapeForMdx()` (correct), you must NOT re-wrap the `signature` field (it's already escaped).
**Why it happens:** The `method` object stores both `signature` (already escaped via `formatMethod`) and `briefDesc`/`detailedDesc` (raw). Only the description fields need wrapping.
**How to avoid:** Apply `escapeForMdx()` at extraction time for `briefDesc`/`detailedDesc` only. Leave `signature` unchanged.
**Warning signs:** Double-escaped output like `&amp;lt;` in generated markdown.

### Pitfall 2: processGroup() README links
**What goes wrong:** `generateModuleOverview()` builds the class list by scanning actual `.md` files in the module directory (`fs.readdirSync(moduleDir)`). After removing namespace names from `utils.classes`, the namespace `.md` files (`Colors.md`, etc.) are still generated by `processNamespace()` before `processGroup()` runs. So the README will still list them — this is correct behavior.
**Why it happens:** `processGroup()` scans the filesystem, not the config. Order of execution matters: classes and namespaces are generated first, then the module overview.
**How to avoid:** Do not change `processGroup()` logic. Simply remove namespace names from `utils.classes`; the namespace pages appear in the README because they're on disk.
**Warning signs:** If you move namespace processing AFTER group processing, namespace pages disappear from the README.

### Pitfall 3: namespace XML file path for `processNamespace`
**What goes wrong:** The generator already finds `namespaceenjin2_1_1Colors.xml` etc. correctly. After removing namespace names from `utils.classes`, the "Warning: XML file not found" messages disappear. Do NOT change the `processNamespace()` path pattern.
**Why it happens:** The warnings were only from the incorrect `processClass()` lookup (looking for `classenjin2_1_1Colors.xml` which doesn't exist). The `processNamespace()` lookup for `namespaceenjin2_1_1Colors.xml` succeeds.
**Warning signs:** Removing warnings by silencing them rather than fixing the root cause.

### Pitfall 4: Running the generator from the wrong directory
**What goes wrong:** The generator uses `__dirname` to compute paths. Running `node generate-api-docs.js` from anywhere works because `__dirname` is always the `scripts/` directory. Running from `docs/` would fail if relative paths were used (they're not).
**How to avoid:** Always run as `node /path/to/scripts/generate-api-docs.js` or from the project root as `node scripts/generate-api-docs.js`. Verify the output "XML directory: /home/unwn/dev/enjin/docs/xml" line matches expectations.

## Open Questions

1. **Should `math::TrigLUT` stay in `utils.classes`?**
   - What we know: `classenjin2_1_1math_1_1TrigLUT.xml` exists; the class is successfully generated as `math_TrigLUT.md`; the `math` namespace is generated as `math.md` via `processNamespace()`.
   - What's unclear: Whether the user expects `math` (namespace) and `math_TrigLUT` (class) as separate sidebar entries, or just one.
   - Recommendation: Keep `math::TrigLUT` in `utils.classes` — it's a class not a namespace, and the current behavior (both `math.md` and `math_TrigLUT.md` in sidebar) is correct and functional.

2. **Should namespace names be added to a separate section in the module README?**
   - What we know: `generateModuleOverview()` scans the directory and lists all `.md` files (both class and namespace pages) under `## Classes`. This label is slightly misleading for namespace pages.
   - What's unclear: Whether renaming the section matters for DOC-01.
   - Recommendation: Out of scope for this phase. The section label does not affect navigability (DOC-01 success criterion). Leave `## Classes` as-is.
