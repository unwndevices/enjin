### E2E Flow: Canvas4 Pixel → Palette Lookup → RGB Display

**Status: WIRED end-to-end. Runtime confirmed 2026-02-24.**

1. `g_canvas` zero-initialized `Canvas4<128,128>` (sdl_main.cpp line 39)
2. `expand_canvas_to_rgb()` iterates all pixels via `g_canvas.getPixel(x, y)` → `Pixel4` with 4-bit index
3. `g_palette.isTransparent(px.value)` — false for indices 0-14, routes to resolve; true (index 15) → black (0,0,0) written
4. `g_palette.resolve(px.value)` → `enjin2::RGB` from PICO-8 default colors[]
5. Written to `g_rgb_staging[i+0/1/2]`
6. `SDL_UpdateTexture(texture, nullptr, g_rgb_staging, CANVAS_W * 3)` line 209
7. `SDL_RenderTexture` with `SDL_SetRenderScale(4.0f, 4.0f)` + `SDL_SCALEMODE_NEAREST` → display

The chain from canvas pixel index through palette lookup to displayed pixel is complete and unbroken.

### E2E Flow: Keyboard → InputState → Edge Detection

**Status: WIRED end-to-end. Runtime confirmed 2026-02-24.**

1. `SDL_PollEvent` drains event queue (lines 187-195)
2. `input_advance_frame(&g_input)` — copies buttons → prev_buttons, zeroes buttons and axes
3. `input_platform_poll(&g_input)` — `SDL_GetKeyboardState(nullptr)`, maps arrows/WASD→bits 0-3, Z→BTN_A, X→BTN_B, Enter→BTN_START
4. `g_input.justPressed(btn)` / `g_input.held(btn)` available to game logic each frame

Note: no game-logic consumer of edge detection yet in sdl_main.cpp — `g_input` is populated but only `SDLK_ESCAPE` is acted upon. Expected; game-logic consumer is Phase 22 scope.

### E2E Flow: Lua Palette API → g_palette → SDL3 Display

**Status: Architecturally sound; physically unreachable until Phase 22.**

`lua_setPaletteColor` and `expand_canvas_to_rgb()` both operate on the same `enjin2::g_palette` object (same `enjin2_graphics` library). A Lua `setPaletteColor(0, 255, 0, 0)` call would be reflected in the SDL renderer's next frame. However, `enjin2_sdl` does not link `enjin2_lua` — no Lua engine is present in the SDL runner. This is the explicit scope boundary of SDL-05, assigned to Phase 22.

### E2E Flow: WASM Canvas4 Pixel → getPaletteRGB → JavaScript Renderer

**Status: WASM path unaffected by Phase 21. Snapshot semantics unchanged.**

The SDL runner and WASM build are separate targets with separate `g_palette` instances at link time. `getPaletteRGB()` snapshot semantics (static buffer populated on call) are not worsened by Phase 21; the SDL runner calls `g_palette.resolve()` live per pixel and never uses `getPaletteRGB()`. JavaScript callers must re-invoke `getPaletteRGB()` after any palette mutation — this calling convention was documented in Phase 19 VERIFICATION.
