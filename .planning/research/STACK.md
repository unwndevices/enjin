# Technology Stack

**Domain:** C++ Codebase Migration and Refactoring
**Researched:** 2025-01-30
**Confidence:** HIGH

## Recommended Stack

### Core Technologies

| Technology | Version | Purpose | Why Recommended |
|------------|---------|---------|-----------------|
| Clang Tooling (LLVM 23.x) | 23.x+ | Static analysis, refactoring, dependency analysis | Industry standard, actively maintained, comprehensive AST-based analysis, supports modern C++ (C++23), extensive check library with automatic fixes |
| Include-What-You-Use (IWYU) | 0.25 (clang 21) | #include dependency analysis | Automatically identifies missing/unnecessary includes, reduces header coupling, improves compilation times, integrates with Clang toolchain |
| CppDepend | 2026.x | Architecture visualization, dependency analysis | Dependency matrices, codebase-wide dependency visualization, AI-assisted insights, enforces coding standards (MISRA, CERT, CWE) |

### Supporting Libraries

| Library | Version | Purpose | When to Use |
|---------|---------|---------|-------------|
| clang-apply-replacements | 23.x | Apply automated fixes in bulk | When running clang-tidy with -fix flag across entire codebase for batch refactoring |
| clang-format | 23.x | Code formatting consistency | Enforce code style during refactoring, integrate into pre-commit hooks, use with --style=file for project-specific configs |
| clang-check | 23.x | Fast syntax checking | Quick validation during iterative refactoring, AST dumping for understanding code structure |
| clang-rename | 23.x | Symbol renaming | Mass renaming of identifiers across codebase with AST-based accuracy |
| LibTooling | 23.x | Build custom analysis tools | When you need project-specific analysis beyond standard clang-tidy checks |

### Development Tools

| Tool | Purpose | Notes |
|------|---------|-------|
| CMake (3.30+) | Build system management | Export compile_commands.json (-DCMAKE_EXPORT_COMPILE_COMMANDS=ON) required by all Clang tools, supports modular builds for incremental migration |
| compile_commands.json | Compilation database | Standard format for Clang tools, auto-generated by CMake, essential for accurate analysis |
| run-clang-tidy.py | Parallel clang-tidy execution | Included with clang-tidy, runs analysis in parallel (-j N), critical for large codebases |
| clang-tidy-diff.py | Analyze incremental changes | Focus analysis on changed files only, useful for CI/PR validation |

## Installation

```bash
# Core Clang tools (Ubuntu/Debian example)
sudo apt-get install clang-tools-23 libclang-23-dev

# Include-What-You-Use
git clone https://github.com/include-what-you-use/include-what-you-use.git
cd include-what-you-use
mkdir build && cd build
cmake -DCMAKE_CXX_COMPILER=clang++ ..
make && sudo make install

# CppDepend
# Download from https://www.cppdepend.com/download/
# Binary distribution available for Linux, Windows, macOS

# Generate compile_commands.json for your project
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

## Alternatives Considered

|-------------|-------------|----------|
| Clang Tooling | SonarQube C++ analyzer | Clang provides deeper C++-specific analysis, easier local setup without server, better integration with build workflow |
| IWYU | Manual header dependency tracking | Automated, handles complex template scenarios, integrates with CMake build, maintains mappings for standard libraries |
| CppDepend | Lattix/Squid/Understand | More modern, AI-assisted insights, better visualization, active development, C++23 support |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|-------------|
| Old GCC-based static analyzers (e.g., splint) | Don't support modern C++ (C++14/17/20/23), poor template support, infrequent updates | Clang Static Analyzer (built into clang-tidy) |
| Header dependency tracking by hand | Error-prone, doesn't scale, misses transitive dependencies, impossible to maintain with templates | IWYU (Include-What-You-Use) |
| Find+grep for dependency analysis | Cannot understand include guards, namespace-based includes, template instantiation dependencies, or conditional compilation | Clang AST-based tools (clang-tidy, LibTooling) |
| Manual refactoring without tools | High risk of introducing bugs, doesn't scale, misses transitive effects of changes | clang-tidy with -fix, clang-rename, LibTooling-based tools |
| Outdated documentation tools (Doxygen 1.8 or older) | Missing C++20/23 support, poor template documentation generation, slow on large codebases | Doxygen 1.16.1+ (released 2026-01-11) |
| Tools without compile_commands.json integration | Cannot accurately parse project-specific defines, include paths, or build flags | Tools that read compile_commands.json (Clang tooling, IWYU, CppDepend) |

## Stack Patterns by Variant

**If migrating to modern C++ (C++17/20/23):**
- Use clang-tidy checks: `modernize-*`, `cppcoreguidelines-*`, `readability-*`
- Run IWYU to clean up include dependencies
- Enable `cppcoreguidelines-avoid-c-arrays`, `modernize-use-nullptr`, `modernize-use-auto`
- Because: These checks identify legacy patterns and suggest modern alternatives, reducing technical debt

**If analyzing architecture for decoupling:**
- Use CppDepend's Dependency Matrix (DSM) and interactive graphs
- Run clang-tidy with `cppcoreguidelines-*` checks
- Use IWYU to identify tight coupling through excessive #includes
- Because: Visualization reveals architectural layers, excessive coupling becomes obvious, enabling targeted refactoring

**If performing mass refactoring (e.g., API changes):**
- Use clang-rename for symbol renaming
- Use clang-tidy with `-fix` and `-export-fixes` for automated fixes
- Use clang-apply-replacements to apply YAML fix files
- Use clang-format to maintain style consistency after changes
- Because: AST-based tools understand scope and transitive references, avoiding manual errors

**If validating migration progress:**
- Use run-clang-tidy.py with `-j` for fast full-codebase analysis
- Use clang-tidy-diff.py for PR/commit validation
- Create .clang-tidy configuration with specific checks enabled/disabled
- Use IWYU to ensure new code follows include discipline
- Because: Parallel analysis reduces validation time, diff-focused analysis prevents regressions, configuration enforces standards

## Migration Workflow (for enjin → enjin2)

### Phase 1: Dependency Analysis

```bash
# 1. Generate compilation database
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON

# 2. Run IWYU on enjin1 to understand include dependencies
iwyu_tool.py -p build/ -- -Xiwyu --max_line_length=120

# 3. Use CppDepend to visualize architecture
# Load enjin1 project, examine Dependency Matrix, identify high-coupling areas

# 4. Run clang-tidy for architecture checks
clang-tidy -p build/ -checks=cppcoreguidelines-*,readability-* src/
```

### Phase 2: Code Movement

```bash
# 1. Identify code to move using dependency analysis
# Use CppDepend's code insight to locate modules that depend on enjin2 features

# 2. Move code to enjin2 with refactoring tools
# Copy files, then run clang-tidy to fix build errors:
clang-tidy -p enjin2/build/ -fix src/new_location/

# 3. Update includes automatically
iwyu_tool.py -p enjin2/build/ -- -Xiwyu --mapping_file=enjin_mappings.imp

# 4. Rename symbols if needed for decoupling
clang-rename -p enjin2/build/ -new-name=NewName old_symbol_name
```

### Phase 3: Validation

```bash
# 1. Run full clang-tidy analysis on enjin2
run-clang-tidy.py -p enjin2/build/ -j$(nproc) -fix

# 2. Verify includes are minimal
iwyu_tool.py -p enjin2/build/

# 3. Format consistently
clang-format -i -style=file src/ include/

# 4. Check for enjin1 dependencies
grep -r "enjin1/" enjin2/src/  # Should return minimal results
```

### Phase 4: Delete enjin1

```bash
# 1. Final validation
# Build enjin2 standalone, run all tests
cmake -S enjin2 -B enjin2/build -DCMAKE_BUILD_TYPE=Release
cmake --build enjin2/build
ctest --test-dir enjin2/build

# 2. Verify no enjin1 dependencies
# Use CppDepend to confirm enjin2 is self-contained
# Run: cppdepend -proj enjin2 -out report.html

# 3. Delete enjin1
rm -rf enjin1/
```
